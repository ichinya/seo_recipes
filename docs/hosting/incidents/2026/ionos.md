## Краткий вывод

В 2026 году у IONOS Cloud заметны три разных класса проблем:

1. реальные деградации управляющего слоя — Managed Kubernetes, Cloud API и Data Center Designer;
2. повышенные ошибки и задержка AI Model Hub;
3. ограничения ёмкости, когда уже работающий сервис доступен, но создать или повторно запустить ресурс нельзя.

Для production это разные риски: первый мешает управлению инфраструктурой, второй влияет на клиентские AI-запросы, третий — на масштабирование и восстановление после остановки.

## AI Model Hub и provisioning 13–14 августа

Деградация AI Model Hub продолжалась с 13 августа до утра 14 августа по UTC. Провайдер сообщал о повышенном уровне ошибок и увеличенной задержке. Это отдельный класс проблемы: виртуальные машины и сети клиента могли работать нормально, но приложение, зависящее от управляемого AI API, получало ошибки или медленные ответы.

14 августа отдельно возникала ошибка provisioning с кодом `VDC-14-1836`. IONOS сообщил об установке hotfix. Её нельзя автоматически считать продолжением деградации AI Model Hub: затронуты разные компоненты платформы.

Для приложения, использующего AI Model Hub, полезны:

- ограничение времени ожидания;
- повтор запросов с экспоненциальной задержкой;
- circuit breaker;
- резервная модель или внешний провайдер;
- отдельный мониторинг доли ошибок и latency API.

## Managed Kubernetes 4–10 августа

Провайдер связывал нестабильность control plane с нагрузкой и ограничениями памяти. В процессе восстановления:

- увеличивались лимиты памяти;
- расширялась базовая инфраструктура;
- клиентские control plane распределялись по дополнительным кластерам;
- выполнялась миграция на улучшенную инфраструктуру.

IONOS отдельно указал, что краткие перерывы control plane не должны были останавливать уже работающие workloads. Это важно: приложение могло продолжать обслуживать трафик, но `kubectl`, API и операции управления кластером — не работать.

## Provisioning 11–12 августа

Проблема относилась к управляющему слою:

- Data Center Designer мог терять соединение;
- операции provisioning выполнялись дольше;
- Cloud API периодически возвращал HTTP 500;
- Terraform, SDK и `ionosctl`, зависящие от API, также могли сталкиваться с ошибками.

Провайдер сообщил, что доступность уже созданных виртуальных дата-центров не пострадала.

## Ограничения ёмкости — не обычный простой

GPU и MongoDB могли показываться как частично недоступные не потому, что все существующие ресурсы остановились, а потому что отсутствовала свободная ёмкость для новых экземпляров.

Это создаёт отдельный риск восстановления: остановленный ресурс нельзя гарантированно запустить снова.

## Практический вывод

- для Kubernetes контролировать отдельно data plane и control plane;
- не считать работающий GPU гарантией возможности повторного запуска;
- перед аварийным восстановлением проверять доступную ёмкость в другой локации;
- IaC-пайплайн должен повторять операции после временных ошибок API;
- AI-интеграция должна иметь тайм-ауты, retries и резервный маршрут;
- для важных кластеров иметь экспорт конфигурации и сценарий развёртывания у другого провайдера.
