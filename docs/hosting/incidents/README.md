# Инциденты хостинг-провайдеров

В этом разделе собрана хронология сбоев, деградаций, DDoS-атак, проблем дата-центров и внешней связности. Журнал нужен не для составления рейтинга по числу аварий, а для поиска повторяющихся рисков и оценки прозрачности провайдера.

Изменения цен, тарифов, локаций, SLA, API и запуск новых услуг не являются инцидентами. Для них используется отдельный раздел [«Изменения хостинг-провайдеров»](../changes/).

## Структура журнала

```text
incidents/
├── 2026/
│   ├── README.md
│   ├── timeweb-cloud.md
│   ├── selectel.md
│   ├── selectel-capacity-october.md
│   ├── regru.md
│   └── events/
│       └── 2026-08-18-mmts9-power-outage.md
└── README.md
```

Страница вида `год/провайдер.md` содержит годовую хронологию провайдера. Подробное дополнение может храниться рядом: оно должно ссылаться на годовой журнал и быть перечислено выше, а последующие обновления тех же событий вносятся в это дополнение без ежедневных дубликатов. Крупные события, которые затронули несколько компаний или общую инфраструктуру, выносятся в `events/` и связываются с журналами затронутых провайдеров.

## Навигация по провайдеру

У страниц инцидентов используются те же теги, что и у [карточек провайдеров](../providers/). Например, тег `Timeweb Cloud` объединяет обзор провайдера, изменения и годовой журнал его инцидентов. Дополнительные теги описывают год и тип проблемы: `DDoS`, `Сеть`, `Электропитание`, `Охлаждение`, `Дата-центры`, `Фильтрация`.

## Правила заполнения

1. Всегда разделять бренд, продукт, локацию и конкретный сервис.
2. Указывать тип источника: официальная status-панель, сообщение провайдера, личный мониторинг, тикет или публикация СМИ.
3. Не подменять неизвестную причину предположением. Если постмортема нет, причина отмечается как неопубликованная.
4. Отделять собственную аварию провайдера от проблем магистрального оператора, внешнего дата-центра, Cloudflare, Hetzner или другого партнера.
5. Не считать плановые работы простоем, но фиксировать окна, в которые недоступно восстановление или управление критичными сервисами.
6. Не добавлять сюда обычное повышение цен, новый тариф или продуктовый релиз: они относятся к `changes/`.
7. Оценивать не только число событий, но и качество коммуникации, наличие постмортема, компенсации и возможность восстановиться из внешней копии.
