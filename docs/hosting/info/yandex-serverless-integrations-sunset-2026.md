# Yandex Serverless Integrations: закрытие и миграция EventRouter

- [Карточка Yandex Cloud](../providers/yandex-cloud.md)
- [Изменения Yandex Cloud за 2026 год](../changes/2026/yandex-cloud.md)

Проверка документации: **11 сентября 2026 года**. Это план подготовки, а не отчёт о выполненной миграции.

## Что закрывается и когда

По [уведомлению о закрытии](https://yandex.cloud/ru/docs/serverless-integrations/sunset), обновлённому 4 сентября:

| Дата | Изменение |
| --- | --- |
| 4 сентября 2026 | Управление Workflows переносится из интерфейса Yandex Cloud в AI Studio |
| 15 сентября 2026 | EventRouter переходит в read-only; создание шин, коннекторов и правил прекращается |
| 8 октября 2026 | Serverless Integrations прекращает работу, его интерфейс закрывается |
| 31 января 2027 | Последняя объявленная дата хранения резервных копий шин, коннекторов и правил; получение — через поддержку |

Workflows переносится автоматически и сохраняется в AI Studio. API Gateway продолжает работать отдельно. Закрывается EventRouter, а не вся serverless-платформа.

Дата обновления документации не является датой первоначального объявления. В уведомлении нет точного часа переключения 15 сентября: подготовку разумно закончить заранее, не рассчитывая на последний вечер. Резервные копии конфигурации не следует считать архивом всех доставлявшихся событий.

## Сначала составить карту зависимостей

Для каждого каталога выполните read-only команды из [официального руководства](https://yandex.cloud/ru/docs/serverless-integrations/tutorials/eventrouter-migration):

```bash
yc serverless eventrouter bus list
yc serverless eventrouter connector list
yc serverless eventrouter rule list
```

Коннекторы и правила перечисляются по каталогу; нужную шину определяйте по `bus_id`. Сохраните конфигурацию, назначьте ответственного и составьте таблицу:

```text
источник → коннектор → правила и фильтры → получатели
                      ↓
              роли / повторы / DLQ / метрики
```

Экспорт и примеры payload могут содержать чувствительные данные. Храните их в закрытом месте, а не в публичном PR или журнале CI. Одного списка имён недостаточно для восстановления настроек.

## Проверить отличия, а не заменить название сервиса

Руководство миграции предупреждает: автоматический перенос подходит не всем шинам и не гарантирует прежнего поведения. Каждый коннектор становится отдельным триггером с получателями всех правил шины; фильтры, преобразования и формат входа нужно сверять отдельно.

Критичные ограничения: не более пяти получателей, размер группы до 64 КиБ вместо 256 КиБ, таймер в UTC. Для сложных действий CLI требует явной группы `yc serverless trigger v2`; старые команды не поддерживают те же параметры. Полную матрицу источников, повторов и DLQ проверяйте в [руководстве](https://yandex.cloud/ru/docs/serverless-integrations/tutorials/eventrouter-migration), а не предполагайте совместимость один к одному.

Практическая проверка для приложения: подготовить обезличенные примеры нормального, повторного и ошибочного события. Для каждого зафиксировать ожидаемые получатели, изменения в БД и поведение при отказе. Новые сервисные аккаунты должны иметь только необходимые роли; не выдавайте общий административный доступ ради упрощения переноса.

## Безопасный тест и переключение

**Message Queue:** тестировать на отдельной очереди. Коннектор и триггер на одной очереди конкурируют за сообщения, а не получают одинаковые копии. **Data Streams:** для тестового параллельного чтения нужен отдельный потребитель; при рабочем переключении важно сохранить позицию чтения. Эти ограничения прямо описаны в официальной инструкции.

Предлагаемый порядок работы:

1. Создать изолированный тестовый контур без отправки настоящих платежей, писем и уведомлений.
2. Сравнить payload и результат обработки с зафиксированными ожиданиями. Проверить повторы и отсутствие двойного бизнес-действия по идентификатору события.
3. Согласовать окно переключения и условия остановки: рост ошибок, пропуски, дубли, накопление очереди или непредвиденные расходы.
4. Переключить источник по его официальной процедуре. Не запускать два активных контура с побочными эффектами без проверенной защиты от дублей.
5. Проверить реальные результаты и метрики, затем удалять старые ресурсы и лишние роли. Не удалять работающую шину до сохранения конфигурации и подтверждения замены.

Наличие API-ответа об успешном создании триггера не подтверждает доставку событий всем нужным получателям.

## Аварийный план

До переключения определить, кто вправе остановить обработку, где сохраняются необработанные события и как выполнить повторную доставку без дублирования результата. Возврат к EventRouter после его отключения нельзя считать доступным rollback. Нужны проверенная конфигурация замены и независимый источник данных для восстановления.

Для Workflows отдельно проверить доступ команды в AI Studio, запуск тестового процесса и действующую автоматизацию. Успешный перенос интерфейса не заменяет проверку конкретного приложения.

## Влияние на оценку

Категория Yandex Cloud **«Рекомендую»** сохраняется. Это прекращение продукта с миграционным риском, не подтверждённая авария всего облака. Отсутствие собственных эксплуатационных тестов отмечено в карточке провайдера.
