# Cloudflare: как проверить фактическую очистку CDN-кеша

**Кейс 20 ноября 2026 года; подготовлено 21 ноября.** Cloudflare зафиксировала две **раздельные региональные** задержки single-file cache purge (`purge by URL`) через Dashboard/API. Это не установленный глобальный отказ CDN и не доказательство отключения origin.

| Регион edge | Первое сообщение, UTC | Финальный `Resolved`, UTC | Екатеринбург (UTC+5) | Официальный источник |
| --- | --- | --- | --- | --- |
| Амстердам | 20.11 18:00 | 20.11 19:41 | 20.11 23:00 — 21.11 00:41 | [Amsterdam](https://www.cloudflarestatus.com/incidents/xsgbfncq7of7) |
| Милан | 20.11 20:51 | 20.11 22:25 | 21.11 01:51–03:25 | [Milan](https://www.cloudflarestatus.com/incidents/akjr7qn5o622) |

В обоих случаях Cloudflare предлагала временный `Purge Everything`, но предупреждала о всплеске запросов к origin. Это **предупреждение**, а не универсальная рекомендация очищать весь кеш. Период между статусными отметками не равен измеренному времени выдачи устаревшего объекта каждому клиенту.

## Дополнение 23 ноября — запросы через EMEA и устаревшие копии в других регионах

[Отдельный инцидент 22 ноября](https://www.cloudflarestatus.com/incidents/5siv904vn94q) затронул **небольшую часть single-file purge-запросов**, поступавших через некоторые дата-центры Европы, Ближнего Востока и Африки. Cloudflare указала окно **19:21–20:21 UTC 22 ноября / 00:21–01:21 23 ноября в Екатеринбурге**. Для этих запросов копии в других точках сети по миру могли оставаться устаревшими до приблизительно 60 минут. Статус — `Resolved`; отложенные операции завершены. Отметка обновления страницы 21:00 UTC не является временем окончания инцидента.

Это самостоятельный эпизод, а не продолжение двух записей за 20 ноября. Регион поступления purge-запроса и регион выдачи старого объекта могут различаться. Практический вывод: одного успешного ответа API или проверки из одной сети недостаточно для оценки нужных пользователю регионов. Заявленные Cloudflare 60 минут не являются измеренной задержкой SEO Recipes или гарантированной длительностью каждого purge.

## Какие три события не стоит путать

1. **Постановка purge-запроса:** API/Dashboard принял запрос. Сам по себе успешный HTTP-ответ не доказывает, что старые копии исчезли из всех edge-локаций.
2. **Инвалидация на edge:** конкретная региональная точка больше не отдаёт прежний кешированный объект. Это надо измерять ответами на **один и тот же URL**.
3. **Доступность origin:** сервер отвечает и выдерживает cache misses. Она независима от успешности purge; `Purge Everything` может временно резко увеличить нагрузку.

Отдельно различайте `Purge by URL`, `Purge Everything`, TTL/expiration, cache rules и браузерный кеш. Смена query string может менять cache key и не доказывает очистку оригинального URL.

## Воспроизводимый безопасный тест

Подготовьте **публичный небольшой статический файл**, который разрешено обновлять, например `/cache-purge-canary.txt`, с явной версией в теле (`version=2026-11-20-a`), стабильным URL и контролируемыми Cache-Control/Cloudflare Cache Rules. Не используйте приватные страницы, персональные данные и подписанные URL.

1. Выберите URL, который непосредственно возвращает **HTTP 200 без редиректа**. Если исходный адрес перенаправляет, сначала определите конечный URL и используйте его во всех измерениях и purge. Измерительный GET не должен следовать редиректам.
2. Зафиксируйте cache key и одинаковые параметры GET: URL, query string, метод и значения включённых в ключ заголовков. Для простой канарейки удобен ключ без cookies и персональных вариантов. Не добавляйте cache-busting query или принудительную revalidation в середине эксперимента.
3. **В каждой точке наблюдения до изменения добейтесь `HIT` со старой версией тела.** Снимите время UTC, `Date`, `Age`, `ETag`, `Cache-Control`, `CF-Cache-Status`, `CF-Ray`, HTTP-код и тело. Точка без исходного старого `HIT` не подходит для измерения задержки purge: новая версия там могла появиться при первом заполнении кеша. Ограничьте число прогревающих запросов; используйте GET, а не только HEAD.
4. Обновите файл на origin и штатным контролем выкладки подтвердите новую версию. До purge ещё раз проверьте, что выбранные точки отдают старый `HIT`. Затем выполните **один разрешённый purge-by-URL**, запишите время отправки и результат принятия запроса. Если custom cache key включает, например, `Accept-Language`, передайте в API те же значения всех составляющих ключа; URL-only purge через Dashboard для такого варианта не подходит.
5. Повторите GET того же URL из тех же независимых регионов/сетей. Сравнивайте **версию тела** и заголовки. Сохраняйте суффикс дата-центра в `CF-Ray`. Если площадка сменилась, пометьте результат как несопоставимый и исключите его из расчёта задержки: свежий ответ нового PoP не подтверждает очистку прежнего. Для новой площадки нужен отдельный цикл с исходным старым `HIT`. Новый `HIT` может содержать свежую версию, а `MISS` сам по себе не доказывает корректность содержимого origin.
6. Заранее задайте интервал и предел наблюдения. Учитывайте TTL и естественное истечение кеша: свежесть после его истечения нельзя приписать только purge. Если обновление не обнаружено за отведённое время, запишите «не подтверждено за окно наблюдения», а не нулевую задержку или бесконечный сбой.
7. Если Cloudflare сообщает о проблемах purge, зафиксируйте инцидент и состояние origin. При действительно критичном обновлении рассмотрите versioned asset URLs / content-hashed filenames. Массовая очистка требует отдельной оценки нагрузки на origin.

Ограничения custom keys и редиректов описаны в [single-file purge](https://developers.cloudflare.com/cache/how-to/purge-cache/purge-by-single-file/). В частности, Cache Rule, совпадающий только с `GET`, может не примениться к purge: проверьте выражение правила до измерения. [Успешный ответ API](https://developers.cloudflare.com/cache/how-to/purge-cache/) подтверждает приём запроса, но не факт удаления объекта.

Пример чтения небольшой публичной канарейки. Сохраните его как Bash-скрипт и выполните до и после purge; вывод каждого запуска сохраните отдельно. Он **не очищает кеш**:

```bash
set -euo pipefail
umask 077
purge_probe_url='https://example.com/cache-purge-canary.txt'
purge_probe_dir="$(mktemp -d "${TMPDIR:-/tmp}/purge-probe.XXXXXXXX")"
trap 'rm -rf -- "$purge_probe_dir"' EXIT

date -u '+observed_at=%Y-%m-%dT%H:%M:%SZ'
purge_probe_code="$(curl --silent --show-error --max-time 10 \
  --max-filesize 65536 \
  --dump-header "$purge_probe_dir/headers" \
  --output "$purge_probe_dir/body" \
  --write-out '%{http_code}' \
  "$purge_probe_url")"

printf 'http_status=%s\n' "$purge_probe_code"
cat "$purge_probe_dir/headers"
if [ "$purge_probe_code" != '200' ]; then
  printf 'Ожидался HTTP 200 без редиректа; результат не сравниваем.\n' >&2
  exit 1
fi
cat "$purge_probe_dir/body"
```

Замените `example.com` собственным доменом. Пример рассчитан на канарейку с простым ключом; при добавлении заголовка, входящего в custom key, одинаковое значение должно присутствовать и в каждом GET, и в purge API. Не публикуйте Cloudflare API tokens, cookies, Authorization и приватные заголовки. Команды здесь не запускались против пользовательского CDN; фактическую задержку нужно измерить в своей среде.

## Последствия для VuePress, WordPress и других сайтов

- **VuePress / статические сборки:** использовать content-hashed имена JS/CSS и безопасный порядок выкладки `assets → HTML`, чтобы обновление не зависело от немедленного глобального purge.
- **WordPress:** после обновления страницы проверить отдельно page cache, object cache, edge cache и кеш браузера. Не путать задержку CDN-инвалидации с работой PHP или изменением поста в БД.
- **SEO:** stale HTML может задержать появление нового title, canonical, robots meta или структурированных данных у отдельных клиентов/роботов. Но конкретное влияние инцидентов Амстердама и Милана на индексацию Google/Яндекса или SEO Recipes не измерялось.

## Что считать доказанным результатом

Публиковать наблюдаемую задержку только при наличии исходного старого `HIT` и последовательности `время purge → время первой подтверждённо свежей версии` для **каждой** тестовой точки. При периодических GET это время обнаружения, а не точный момент инвалидации: укажите интервал опроса и время последнего старого ответа. Официальное время `Resolved` описывает состояние инцидента у Cloudflare и не заменяет клиентский эксперимент. Обязательно укажите регион, сетевого провайдера/ASN, URL-класс, настройки кеширования и метод измерения.
