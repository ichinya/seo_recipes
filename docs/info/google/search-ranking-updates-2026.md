# Обновления ранжирования Google Search в 2026 году

Журнал начат **27 сентября 2026 года** с текущего September spam update. Это накопительная подборка проверенных событий, **не полный архив с января**. Отсутствие более ранних строк не означает, что других обновлений в 2026 году не было.

Здесь хранятся даты и официальные сообщения. Подробная методика диагностики уже описана в [руководстве по разбору падения после core update](./core-update-recovery.md); возможности отчётности — в [материале о Search Console](./search-console-2026.md). Данные конкретного сайта при подготовке журнала не анализировались.

Для сопоставления с журналами в UTC начало соответствует **24 сентября, 16:15 UTC**. Часовой пояс источника сохранён явно: календарные даты отчётов и серверных логов нельзя сравнивать без учёта их зон.

### 24 сентября — September 2026 spam update

В [официальной карточке](https://status.search.google.com/incidents/XhUDXP7A67iHCD2kmbVu) указаны глобальный охват, все языки и ожидаемая продолжительность rollout **до двух недель**. Это оценка развёртывания, а не подтверждённая дата окончания и не срок восстановления позиций.

При повторном чтении **5 октября 2026 года** [общая панель Google](https://status.search.google.com/) по-прежнему показывает `Active`, а карточка содержит только начальное сообщение **24 сентября, 09:15 PDT**. Отметка обновления самой панели — **4 октября, 22:17 PDT** (**5 октября, 10:17 по Екатеринбургу, UTC+5**) — не является новым сообщением об апдейте. Статус не изменился относительно проверок 27 и 30 сентября и 4 октября; завершение не объявлено. Итоговую длительность rollout и дату начала анализа «после завершения» пока не фиксируем. Новая контрольная отметка не является существенным изменением алгоритма и сама по себе не требует отдельной новости в следующей сводке.

Google называет событие spam update. В прочитанном анонсе нет отдельного списка ниш, сайтов или технологий, на которые оно нацелено. Нельзя на этом основании объявлять его специально обновлением против AI-текстов, ссылочного спама или конкретного языка.

## Как различать события

[Документация панели](https://developers.google.com/search/help/status-dashboard) разделяет информацию об изменениях систем и сообщения о нарушении их работы. Само наличие ranking update не означает недоступность Google Search. Отсутствие аварии на панели также не доказывает исправность конкретного сайта.

Для этого журнала используем следующий порядок классификации:

| Сигнал | Как записывать |
| --- | --- |
| Официально названный core update | Самостоятельная строка с типом Core |
| Официально названный spam update | Тип Spam без предположений о конкретной подкатегории |
| Явно названный link spam update | Отдельно обозначить ссылочную направленность |
| Другое официальное обновление | Сохранить название и заявленный охват |
| Сбой crawling, indexing или serving | Не выдавать за новый алгоритмический апдейт; учитывать отдельно при диагностике |
| Manual action конкретного сайта | Не записывать как глобальный rollout |
| Всплеск стороннего «датчика волатильности» | Наблюдение, не подтверждённая дата релиза Google |

Автоматическое выявление спама и ручные меры — разные механизмы: [spam policies](https://developers.google.com/search/docs/essentials/spam-policies) описывают оба. Нарушение нельзя диагностировать только по совпадению падения графика с началом апдейта.

## Что делать во время активного rollout

Начните с сохранения фактов, а не массового переписывания сайта. В собственном журнале изменений отметьте начало апдейта, релизы сайта, миграции, недоступность сервера и изменения аналитики. Для каждой гипотезы сохраняйте наблюдение, источник и то, чего пока не удалось установить.

По [официальной инструкции диагностики трафика](https://developers.google.com/search/docs/monitor-debug/debugging-search-traffic-drops) проверьте технические ошибки, Security Issues, Manual Actions и известные аномалии данных Search Console. Падение может быть связано с сезонностью, изменением спроса, переносом URL или обработкой статистики, а не только с ранжированием.

Для повторяемой проверки нескольких URL после релиза есть [рецепт Browser Run](../../hosting/testing/cloudflare-browser-run-seo-audit.md). Такой технический аудит помогает обнаружить изменения HTTP/DOM, но не доказывает влияние алгоритмического апдейта.

**Не откладывайте устранение взлома, ошибок доступа или случайного `noindex` до конца rollout.** Осторожность с SEO-экспериментами не является запретом на срочный ремонт и обновления безопасности.

Простой рабочий протокол для команды:

1. Зафиксировать URL официального события и время последней проверки, не подменяя ими время начала.
2. Сохранить исходные выгрузки и применённые фильтры, отдельно описать параллельные изменения сайта.
3. Проверить несколько затронутых URL вручную и через доступные диагностические отчёты.
4. Исправлять подтверждённые проблемы; для остальных гипотез выбрать небольшую проверяемую группу страниц вместо массового удаления разделов.

## Сравнение после завершения

Вначале дождитесь **официального сообщения об окончании**, затем обновите строку журнала. Для core updates Google рекомендует [выждать хотя бы полную неделю после завершения](https://developers.google.com/search/docs/appearance/core-updates) и сравнить её с неделей перед началом. Это рекомендация для анализа **core update**, не универсальный срок восстановления после spam update.

Для собственного отчёта можно использовать такую схему; это организационный шаблон, а не обязательный стандарт Google:

| Поле отчёта | Что сохранить |
| --- | --- |
| Событие | Название, начало, официальное окончание, источник |
| Периоды | Сопоставимые интервалы одинаковой длины, по возможности вне rollout |
| Группы | Те же страницы, запросы, страны, устройства и тип поиска |
| Метрики | Клики, показы, CTR и позиция вместе, а не один средний показатель |
| Помехи сравнению | Релизы, миграции, аварии, сезонность, неполные данные |
| Вывод | Наблюдаемое изменение, альтернативные объяснения, следующий тест |

Google рекомендует [проверять срезы и типы поиска раздельно](https://developers.google.com/search/docs/monitor-debug/debugging-search-traffic-drops). Сравнение одинаковых групп уменьшает смешение эффектов, но не доказывает причинность. Не подменяйте отсутствующие или ещё неполные данные нулями и не называйте разницу в два дня итогом длительного апдейта.

### Если предполагается нарушение spam policies

Проверьте реальные практики сайта по [действующим правилам](https://developers.google.com/search/docs/essentials/spam-policies), а не по слухам о «секретном факторе». Запишите конкретные примеры и изменения; само использование генератора текста не заменяет проверку соответствия правилам.

Google [предупреждает](https://developers.google.com/search/docs/appearance/spam-updates), что системам может потребоваться несколько месяцев, чтобы распознать устойчивое соответствие правилам. Это не гарантия роста. Для отдельно объявленных link spam updates потерянную выгоду от нейтрализованных спамных ссылок нельзя считать обещанной к возврату. К сентябрьскому событию ссылочную направленность без отдельного заявления не приписываем.

## Как поддерживать журнал

Следующее сообщение о том же rollout дополняет **существующую строку**, а не создаёт новую ежедневную статью. Полезно хранить название, постоянный URL, начало с часовым поясом, фактическое окончание, заявленный охват и дату проверки.

Оценка продолжительности не закрывает запись автоматически. Если источник не загрузился, сохраните последний подтверждённый статус с прежней датой; не объявляйте проверку успешной. Новая дата обновления всей панели не означает новый этап конкретного события.

За объявлениями можно следить через RSS, ссылка на который есть на [Search Status Dashboard](https://status.search.google.com/). Добавление прошлых событий требует отдельной проверки архива; год в заголовке не является заявлением о его полноте.
