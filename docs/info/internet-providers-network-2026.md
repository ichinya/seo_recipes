### Практическая проверка сайта

Измеряйте один разрешённый URL с фиксированного доступа и нескольких мобильных сетей в близком временном окне. Записывайте оператора, ASN, регион, время, наличие VPN/прокси, DNS, IPv4/IPv6, TLS, HTTP и ожидаемое содержимое. Рабочий Wi-Fi, использующий тот же мобильный uplink, не является независимой контрольной точкой.

Разрешение DNS или видимость маршрута в BGP ещё не подтверждает загрузку сайта. Не называйте такие ограничения аварией VPS и не снижайте оценку хостинга только из-за жалоб мобильных абонентов. Влияние на посещаемость, индексирование и позиции SEO Recipes без собственных данных не установлено. Не отключайте защиту и не меняйте DNS автоматически; используйте шаблон наблюдения ниже.

### Что проверить владельцу сайта

Разделите недоступность приложения провайдера, доступ абонента к интернету и доступность своего URL через эту сеть. Сравните одинаковые URL из нескольких ASN в близком временном окне; отдельно проверьте DNS, IPv4/IPv6, TLS и ожидаемое тело HTTP-ответа. При доступном интернете, но недоступном личном кабинете, не называйте это общим отказом сети.

Сверьте логи origin и CDN, ошибки браузера и изменения своей инфраструктуры. Пока нет измерений конкретного сайта, влияние на его индексирование, посещаемость и позиции не установлено. Не отключайте защиту и не переключайте DNS только по числу жалоб. Шаблон записи наблюдений приведён ниже.

## Правила ведения журнала

1. Для каждой записи указывать **дату события**, **дату публикации** и **дату проверки**, сохраняя часовой пояс. Дата обновления страницы не означает новое событие.
2. Сначала искать подтверждение у оператора/регулятора и в измерительных данных: [RIPE RIS](https://ris.ripe.net/), [RIPEstat](https://stat.ripe.net/), [IODA](https://ioda.inetintel.cc.gatech.edu/), [Cloudflare Radar](https://radar.cloudflare.com/), [RouteViews](https://www.routeviews.org/). 3. Различать **доступность сайта**, **доступность сети оператора**, **BGP-видимость префиксов** и **жалобы пользователей** — эти показатели не эквивалентны.
4. Не объявлять сбой общероссийским без независимого подтверждения географии. Не приписывать отключения DPI, ТСПУ или блокировкам без проверяемых данных.
5. Фиксировать тип воздействия: потеря связности, повышенный RTT или loss, DNS, IPv4/IPv6, маршруты/пиринг, тарифы и ограничения. Для каждого указывать практические последствия для сайтов, ботов поиска, мониторинга и аналитики.
6. Не создавать отдельные статьи по небольшим локальным жалобам; сначала накапливать датированные наблюдения. По подтверждённым крупным случаям заводить отдельный разбор с измерениями и ограничениями вывода.

## Как проверять сетевую проблему сайта

- Сверить часы и окно события в UTC и МСК, затем проверить URL из **нескольких провайдерских сетей и регионов**.
- Отдельно проверить DNS-ответы, IPv4 и IPv6, TCP/TLS и HTTP-коды; успех на одной сети не доказывает доступность во всех остальных.
- Сопоставить RTT, packet loss, трассировки и маршруты с контрольным периодом. Не принимать один traceroute или ICMP timeout за доказательство сбоя на конкретном узле.
- Если есть BGP-аномалия, зафиксировать ASN, затронутые префиксы и время по нескольким коллекторам; BGP withdrawal не всегда означает полную пользовательскую недоступность.
- Только после проверки влияния на конкретные URL решать, нужны ли изменения CDN/DNS, инфраструктуры или уведомление пользователей. Не запускать автоматические переключения по единичной жалобе.

### Карточка воспроизводимого наблюдения

Ниже — **редакционный шаблон проверки**, а не результаты измерения TENET или SEO Recipes. Проверки выполняет владелец сайта либо уполномоченный оператор с небольшим числом запросов, без нагрузочного тестирования чужих сервисов.

| Поле | Что записать |
| --- | --- |
| Время | Начало и конец пробы в UTC, часовой пояс исходного уведомления и дата его публикации |
| Точка проверки | Идентификатор пробы, ASN и регион, источник этих сведений; отдельно наличие VPN или прокси |
| Цель | Один и тот же разрешённый URL, метод GET и ожидаемый признак страницы; без токенов в query string |
| DNS | Использованный резолвер, ответы A/AAAA, TTL или точная ошибка; отсутствие AAAA не считать сбоем IPv6 |
| IPv4 / IPv6 | Две отдельные пробы при наличии соответствующих DNS-записей и связности у проверяющего узла |
| TCP / TLS | Подключение, ошибка или тайм-аут, имя SNI и результат проверки сертификата; не отключать TLS-проверку |
| HTTP | Код, цепочка редиректов и ожидаемое содержимое; страница ошибки или входа с кодом 200 не считается успехом |
| Время ответа | DNS, TCP, TLS, TTFB и общее время, версия инструмента, тайм-аут и число повторов |
| Сопоставление | Те же URL из независимых ASN в близком временном окне и контроль до/после события; одинаковый IP CDN не предполагается |
| Вывод | Что наблюдалось, возможные альтернативные причины и что осталось неизвестным |

Отсутствие проверки помечать как «не измерено», а не как «доступно» или нулевое время. Проверка из одной домашней сети не заменяет независимые пробы. Из публичного отчёта исключать cookies, токены, личные адреса абонентов и приватные адреса инфраструктуры; исходные чувствительные логи хранить в закрытом доступе.

> **Ограничение:** это редакционный журнал подтверждённых уведомлений и осторожно отмеченных сигналов, а не сервис онлайн-мониторинга и не рейтинг качества интернет-провайдеров.
